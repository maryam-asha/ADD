# الدفع بالبطاقة — دليل تطبيق الموبايل

مرجع مطوّر التطبيق لتنفيذ الدفع بالبطاقة عبر Paymera eGate، ولدفع أي عملية
(حجز، جلسة، فعالية، باقة) بالمحفظة أو في الاستقبال — انظر القسم 11، وللعروض وكوبونات الحسم القسم 12.

> **الخلاصة في ثلاث خطوات:** اطلب رابط دفع من الـAPI ← افتحه في WebView ←
> اسأل الـAPI عن النتيجة. التطبيق **لا يتصل بـPaymera إطلاقاً**، ولا يرى
> مفتاح الـAPI، ولا يقرر بنفسه أن الدفع نجح.

رقم البطاقة ورمز الـOTP (5 أرقام، 3 محاولات) يُدخلان في صفحة Paymera داخل
الـWebView — لا يمران عبر التطبيق ولا عبر خادمنا.

---

## 1. المصادقة

كل مسارات الأعضاء تستخدم توكن العضو المعتاد:

```http
Authorization: Bearer <access_token>
Accept: application/json
lang: ar
```

هو نفسه التوكن الصادر عن `POST /api/v1/auth/login`. لا يوجد توكن خاص بالدفع.

---

## 2. بدء دفع بالبطاقة — شحن المحفظة وشراء باقة

لا يوجد مسار عام للدفع: كل عملية تُدفع عبر مسارها الخاص، وكلها تردّ بالحقول
نفسها (`payment` و`redirect_url` و`next`) فتُفتح `redirect_url` في WebView كما
في القسم 3. موضع الحقول يختلف: داخل `data` في الشحن والباقة وتسجيل الفعالية
(الإنشاء وإعادة الإرسال بـ`ticket_id`) والجلسة المغلقة، وبجانب `data` في
الحجز (الإنشاء وإعادة الإرسال بـ`booking_id`، القسم 11-ب). هذا القسم لشحن
المحفظة (بالبطاقة دائماً) ولشراء الباقة (الافتراضي `wallet`، ويقبل `cash`
و`paymera`)؛ الحجز وتسجيل الفعالية والجلسة في القسم 11.

### أ. شحن المحفظة

```http
POST /api/v1/member/wallet/top-ups
```

```json
{
  "amount": "1470000"
}
```

`amount` بالوحدات الكبرى للعملة المشحونة (ليرة سورية) — أي `1470000` تعني
1,470,000 ل.س. **لا ترسل قروشاً ولا فواصل ولا رموز عملة.**

الشحن بطريقة مسبقة الدفع فقط (البطاقة): `payment_method` اختياري وافتراضيه
البطاقة، وأي طريقة لا تصلح للشحن (`cash`، `wallet`) ← 422. شحن النقاط نقداً
يتم في الاستقبال، لا من التطبيق.

### ب. شراء باقة

```http
POST /api/v1/member/memberships
```

```json
{
  "plan_id": 7,
  "payment_method": "paymera"
}
```

لغة صفحة Paymera تؤخذ من الهيدر `lang` (`ar` أو `en`، والافتراضي `ar`) —
لا تُرسل في جسم الطلب.

**لا ترسل `amount` هنا.** السعر يُقرأ من قاعدة البيانات، وأي `amount` مرسل
يُتجاهل تماماً. هذا مقصود: العميل لا يحدد ما سيُخصم من بطاقته.

### الحقول

| الحقل | المسار | إلزامي | الوصف |
|---|---|---|---|
| `amount` | `wallet/top-ups` | نعم | نص/رقم، بالوحدات الكبرى، ≥ 0.01، رقم عشري عادي (`10` أو `10.50`) — صيغة الأُس مثل `1e3` ← 422 |
| `payment_method` | `wallet/top-ups` | لا | بطاقة فقط (`paymera`)، وهي الافتراضية |
| `plan_id` | `memberships` | نعم | معرّف باقة متاحة للبيع |
| `payment_method` | `memberships` | لا | `paymera` للبطاقة؛ الافتراضي `wallet` (انظر القسم 11-ج) |

### الرد الناجح — 201

```json
{
  "data": {
    "payment": {
      "id": 12,
      "status": "pending",
      "purpose": "wallet_top_up",
      "amount_minor": 147000000,
      "currency": "SYP",
      "currency_exponent": 2,
      "points_to_credit": 1000,
      "plan_id": null,
      "membership_id": null,
      "rrn": null,
      "created_at": "2026-09-27T12:48:07.000000Z"
    },
    "redirect_url": "https://egate-t.paymera.cc/start/{paymentId}/ar",
    "next": "redirect"
  }
}
```

احفظ `data.payment.id` — ستحتاجه للاستعلام — وافتح `data.redirect_url`.

### الأخطاء

| الرمز | المعنى | ما يُعرض للمستخدم |
|---|---|---|
| `422` | خطأ تحقق (`errors` يحوي التفاصيل) | رسالة الحقل |
| `503` | البوابة غير متاحة (إعداد لدينا) | "الدفع بالبطاقة غير متاح مؤقتاً" |
| `502` | تعذّر بدء العملية | "تعذّر بدء الدفع، حاول ثانية" |

**503 و502 ليسا رفضاً للبطاقة** — لم تُشحن البطاقة أصلاً، والخلل عندنا.
لا تعرضهما كـ"فشل الدفع".

## 3. تدفق الـWebView

1. افتح `redirect_url` في WebView.
2. راقب التنقل: عندما يصبح الرابط محتوياً على **`/api/v1/paymera/callback/`**
   فقد انتهى المستخدم (سواء بالدفع أو بالإلغاء).
3. أغلق الـWebView.
4. انتقل إلى الاستعلام عن الحالة (القسم 4).

```
افتح redirect_url في WebView
        │
   المستخدم يدخل البطاقة + OTP على صفحة Paymera
        │
   الرابط يحوي /api/v1/paymera/callback/  ←── إشارة الانتهاء
        │
   أغلق الـWebView ثم استعلم عن الحالة
```

> **مهم:** الوصول إلى صفحة الـcallback **لا يعني النجاح**. المستخدم يصلها
> أيضاً بالضغط على Cancel. المصدر الوحيد للنتيجة هو استعلام الحالة.

متطلبات الـWebView: تفعيل JavaScript والـcookies، والسماح بالتوجيه
(redirects). لا تعترض أي رابط آخر ولا تحقن أي سكربت في صفحة البنك.

## 4. الاستعلام عن الحالة

```http
GET /api/v1/member/payments/{id}
```

```json
{
  "data": {
    "id": 12,
    "status": "accepted",
    "purpose": "wallet_top_up",
    "amount_minor": 147000000,
    "currency": "SYP",
    "currency_exponent": 2,
    "points_to_credit": 1000,
    "plan_id": null,
    "membership_id": null,
    "rrn": "000053127772",
    "created_at": "2026-09-27T12:48:07.000000Z"
  }
}
```

> **انتبه للفرق:** هنا البيانات في `data` مباشرة، بينما في رد الإنشاء (201)
> كانت داخل `data.payment`. هذا مصدر خطأ شائع.

الخادم يسأل البوابة عند كل استعلام، والعملية محمية بقفل وغير قابلة للتكرار،
**فالاستعلام المتكرر آمن ولا يشحن النقاط مرتين.**

### سياسة الاستعلام المقترحة

استعلم بعد إغلاق الـWebView مباشرة، ثم أعد المحاولة بتباعد متزايد
(1s، 2s، 4s، 8s) لنحو 30 ثانية. إن بقيت `pending` فاعرض "سنؤكد العملية
خلال دقائق" — مهمة مجدولة تسوّي كل دفعة معلّقة خلال 5 دقائق على أي حال،
فلا حاجة لإبقاء المستخدم منتظراً.

---

## 5. حالات `status` وكيف تُعرض

| `status` | المعنى | ما يُعرض |
|---|---|---|
| `pending` | لم تُحسم بعد | "جارٍ التحقق…" وتابع الاستعلام |
| `accepted` | نجحت، والنقاط أُضيفت | نجاح ✅ |
| `failed` | رفض البنك أو خطأ OTP | فشل — لم يُخصم شيء |
| `canceled` | ألغى المستخدم | إلغاء — لم يُخصم شيء |
| `expired` | انتهت مهلتها دون حسم | فشل — اطلب إعادة المحاولة |
| `needs_review` | **ليست فشلاً** | "قيد المراجعة" + تواصل مع الدعم |
| `reversed` | أُلغيت من قبل الإدارة بعد نجاحها | مُستردّة |

### `needs_review` — الحالة التي يجب عدم إساءة عرضها

تعني أن المال أُخذ ويحتاج تدخلاً بشرياً. **لا تعرضها كفشل**، ولا تدعُ
المستخدم لإعادة الدفع — فقد يدفع مرتين.

الحالة الخاصة في شراء الباقات: `status = "needs_review"` مع
**`membership_id = null`** تعني: "أُخذ المال، والنقاط في محفظتك، لكن الباقة
لم تُفعّل". النقاط **لم تضِع**. اعرض ما يناسب ذلك ووجّه المستخدم للدعم.

---

## 6. عرض المبالغ

المبلغ يأتي كعدد صحيح من الوحدات الصغرى مع الأُس:

```
القيمة المعروضة = amount_minor / (10 ^ currency_exponent)
147000000 / 10^2 = 1,470,000.00 ل.س
```

**لا تُحوّل `amount_minor` إلى float ولا تعتمد قسمة عشرية جاهزة.** استخدم
حساباً صحيحاً أو مكتبة decimal، واعرض العملة من `currency`.

`points_to_credit` هو عدد النقاط التي ستُضاف — وهو مثبَّت لحظة إنشاء
الدفعة، فلا يتغير إن تغيّر سعر النقطة أثناء الدفع.

## 8. الحقول المتاحة للعضو

أحد عشر حقلاً فقط:

`id` · `status` · `purpose` · `amount_minor` · `currency` ·
`currency_exponent` · `points_to_credit` · `plan_id` · `membership_id` ·
`rrn` · `created_at`

`rrn` هو الرقم المرجعي البنكي — اعرضه في إيصال النجاح، فهو ما يُستشهد به
عند أي نزاع (يطابق عمود `Trans RRN` في لوحة Paymera).

حقول أخرى (`terminal_id`، `review_reason`، `gateway_payment_id`…) متاحة
للوحة الإدارة فقط ولن تصل التطبيق.

---

## 9. أخطاء شائعة يجب تجنّبها

- ❌ اعتبار وصول الـWebView إلى صفحة الـcallback نجاحاً — استعلم دائماً.
- ❌ قراءة `data.status` في رد الإنشاء — هناك المسار `data.payment.status`.
- ❌ إرسال `amount` مع شراء باقة — يُتجاهل.
- ❌ إنشاء حجز (أو تسجيل) جديد بعد فشل البطاقة بدل إعادة الإرسال مع
  `booking_id` (أو `ticket_id`).
- ❌ عرض `needs_review` كفشل ودعوة المستخدم للدفع ثانية.
- ❌ تحويل `amount_minor` إلى float.
- ❌ محاولة استدعاء Paymera مباشرة من التطبيق.
- ❌ اعتبار 502/503 رفضاً للبطاقة.

## 11. الدفع لأي عملية — المحفظة، الاستقبال، البطاقة

كل عملية تُدفع عبر مسارها الخاص — لا يوجد مسار عام للدفع (المسار القديم
أُزيل) — وكلها تردّ `payment` و`redirect_url` و`next` بالمعنى نفسه (الجدول في
(ب) أدناه). أما `GET member/payments` و`GET member/payments/{id}` فباقيان:
سجلّ العضو، وما يُستعلم عنه بعد إغلاق الـWebView (القسم 4).

### أ. معرفة طرق الدفع

خدمة واحدة تُرجع طرق الدفع المتاحة للعضو، بتوكن العضو المعتاد:

```http
GET /api/v1/member/payment-methods
Authorization: Bearer <access_token>
```

- طريقة `wallet` تحمل نقاط العضو: `balance` (أكبر رصيد يمكنه الصرف منه)
  و`wallets` (الشخصية ومحافظ الشركات، لكلٍّ رصيدها). إذا كان الرصيد صفراً
  تكون `available: false` مع `reason: "لا يوجد رصيد في محفظتك"`.
- كل الباراميترات اختيارية. `purpose` يُبقي الطرق التي تدفع هذه العملية
  فقط (شحن المحفظة: البطاقة فقط، بلا نقد وبلا تلميح "اذهب إلى الاستقبال")،
  ومعه `payable_id` (أو `plan_id`) يُعاد
  `amount_points` و`price`، وهل يكفي الرصيد لها. مفيد مثلاً لأن نقاط
  الباقة المخصّصة للمساحات تُحسب عند `purpose=booking` فقط.

```json
{
  "data": {
    "amount_points": null,
    "price": null,
    "price_point": null,
    "methods": [
      {"key": "wallet", "label": "نقاط المحفظة", "available": true, "reason": null, "balance": 400,
       "wallets": [{"owner_type": "user", "owner_id": 7, "owner_label": "Personal", "usable_balance": 400, "sufficient": true}]},
      {"key": "cash", "label": "نقداً في الاستقبال", "available": true, "reason": null},
      {"key": "paymera", "label": "بطاقة", "available": true, "reason": null}
    ]
  }
}
```

اعرض الطرق **بالترتيب الذي تصل به** وحسب `key`، ولا تفترض قائمة ثابتة: أي
طريقة جديدة (مثل Sham Cash لاحقاً) تُضاف من الخادم وتظهر هنا وحدها.
`GET member/wallet/options` لم يعد لازماً للتطبيق.

### ب. الدفع لاحقاً أو بطريقة أخرى — الطلب نفسه مع المعرّف

الحجز وتسجيل الفعالية يُنشآن أولاً ثم يُدفعان. لتغيير طريقة الدفع — بعد فشل
بطاقة، أو لدفع حجز نقدي لاحقاً — **أعد إرسال طلب الإنشاء نفسه مع معرّف
السجل**: لا يُنشأ شيء ولا تُطبَّق أي قاعدة من قواعد الإنشاء (الموعد، المهلة،
السعة، نموذج التسجيل)؛ تتغير طريقة دفع السجل فقط. احتفظ بالمعرّف من ردّ
الإنشاء الأول. الجلسة المغلقة ليس لها طلب إنشاء يُعاد، فلها مسار `pay`.

**الحجز** — `POST /api/v1/member/bookings`:

```json
{
  "booking_id": 15,
  "payment_method": "wallet",
  "wallet_owner_type": "company",
  "wallet_owner_id": 3
}
```

- `booking_id` هو `data.id` من ردّ إنشاء الحجز، وحجز العضو نفسه فقط.
  `payment_method` إلزامي كما في الإنشاء.
- `space_id` و`start_at` و`end_at` اختيارية مع المعرّف: يمكن للتطبيق إرسال
  قيم شاشة التأكيد كما هي، لكن أي قيمة تُرسل يجب أن تطابق الحجز وإلا 422
  `booking_mismatch` ("ابدأ الحجز من جديد").
- `wallet_owner_type/id` اختياريان، وتُقرأ **مع `wallet` فقط**: محفظتك
  الشخصية أو محفظة شركة أنت عضو فيها؛ إذا كان للعضو أكثر من محفظة ولم يحدد،
  يعود 422 مع `wallet_options`. مع البطاقة أو النقد يذهب المال دائماً إلى
  محفظتك الشخصية أولاً، مهما أُرسل في هذين الحقلين.
- `coupon_code` اختياري (القسم 12-د). أرسله كما أرسلته عند الإنشاء: الكود
  الذي يحمله الحجز أصلاً يُتجاهل بلا خطأ. وكود لا يمكن تطبيقه الآن — لا يُجمع
  مع العرض الذي سُعّر به الحجز (`not_combinable`)، أو توجد دفعة بالبطاقة قيد
  التنفيذ (`payment_in_progress`) — **لا يمنع الدفع**: يعود
  `coupon.applied: false` مع `message`، ويمضي الدفع بسعر الحجز الحالي. أما
  بقية أسباب الرفض (كود غير صالح، منتهٍ…) فتبقى 422 كما عند الإنشاء.
- الرد 200: `{"data": {الحجز}, "payment": {...}, "redirect_url": "...",
  "next": "...", "coupon": {...}}` — الحقل `coupon` فقط إن أُرسل كود
  (ولا يوجد إن كان الكود هو نفسه المطبَّق على الحجز).

**تسجيل فعالية** — `POST /api/v1/member/events/{id}/register`:

```json
{
  "ticket_id": 31,
  "payment_method": "paymera"
}
```

- `ticket_id` هو `data.ticket_id` من ردّ التسجيل، وتسجيل العضو نفسه في هذه
  الفعالية فقط. **لا ترسل حقول نموذج التسجيل**، ولا تُفحص مهلة التسجيل ولا
  السعة.
- `payment_method` اختياري هنا: إن لم يُرسل فالدفع من محفظة العضو الشخصية
  (كما في التسجيل بلا طريقة)، ولا يُسأل عن الاختيار بين المحافظ.
- إشعار `event.payment_due` يحمل في `data` الحقول `event_id` و`payable_id`
  (وهو `ticket_id`)، وهما كل ما يلزم لإعادة الإرسال من الإشعار.
- الرد 200: `{"data": {"ticket_id": 31, "status": "approved", "payment": {...},
  "redirect_url": "...", "next": "..."}}` — الحقل `coupon` (إن أُرسل كود) داخل
  `data` هنا. وكود لا يمكن تطبيقه (لا يُجمع مع العرض، أو دفعة قيد التنفيذ)
  يعود `coupon.applied: false` ويمضي الدفع بالسعر الحالي، كما في الحجز.
- تسجيل **بانتظار الموافقة** وغير مدفوع: تُحفظ الطريقة المختارة فقط ولا
  يُخصم شيء قبل الموافقة، فيعود `next: "pay_at_reception"` و`payment: null`.
  هذا `next` لا يعني "ادفع في الاستقبال": لا شيء يُدفع قبل الموافقة، ولذلك
  يعرض التطبيق "بانتظار الموافقة" من `status` (`pending`) لا من `next`.

**جلسة كوورك مغلقة غير مدفوعة** — `POST /api/v1/member/coworking-sessions/{type}/{id}/pay`
حيث `{type}` هو `booking` أو `walkin` (من تقرير الجلسة):

```json
{
  "payment_method": "paymera"
}
```

`wallet_owner_type/id` و`coupon_code` اختياريان كما أعلاه. الرد **201**:
`{"data": {"payment": {...}, "redirect_url": "...", "next": "..."}}` ومعه
`coupon` بجانب `data` إن أُرسل كود. الجلسة المفتوحة لا تُدفع قبل إغلاقها
(422).

**الأخطاء المشتركة:**

| الرمز | المعنى |
|---|---|
| `404` | السجل ليس للعضو (أو ليس تسجيله في هذه الفعالية) |
| `409` | مدفوع مسبقاً (`already_paid`) |
| `422` | حجز ملغى أو مرفوض أو لم يُحضر إليه (`booking_not_payable`) · قيم لا تطابق الحجز (`booking_mismatch`) · لا مبلغ مستحق (`nothing_due`) · نقاط غير كافية `{message, current, required, shortage}` · محفظة تحتاج اختياراً (`wallet_options`) · كوبون مرفوض (القسم 12-هـ) |
| `503` / `502` | البوابة غير متاحة / تعذّر فتح الدفع — ليسا رفضاً للبطاقة (القسم 2) |

وفي كل الحالات الرد (الحجز، التسجيل، الجلسة) يحمل `next`:

| `next` | ماذا يفعل التطبيق |
|---|---|
| `redirect` | يفتح `redirect_url` في WebView ثم يستعلم `GET payments/{id}` كما في القسم 3 و4 |
| `done` | دُفع الآن من المحفظة — حدّث الشاشة |
| `pay_at_reception` | لا شيء يُدفع الآن؛ اعرض "ادفع في الاستقبال". قد يكون `payment` هنا `null` |

**بطاقة فشلت أو أُغلقت قبل الدفع** ← أعد الإرسال مع المعرّف بالطريقة التي
اختارها العضو الآن (محفظة أو نقد أو بطاقة جديدة). لا تُنشئ حجزاً ثانياً:
الحجز الأول لا يزال قائماً وموعده محجوز به، فسيُرفض الثاني لأن الموعد
مأخوذ بحجزك أنت.

### ج. الدفع عند الإنشاء

- **الحجز:** `POST member/bookings` يقبل `payment_method`. `wallet` يدفع
  الآن أو يرفض بـ 422 ولا يُنشأ الحجز؛ `cash` ينشئه غير مدفوع؛ `paymera`
  ينشئه غير مدفوع ويضيف بجانب `data` الحقلين `payment` و`redirect_url`
  (احتفظ بـ`data.id` لـ(ب)). إن
  تعذّر فتح صفحة البطاقة (البوابة أو سعر الصرف غير متاحين) يبقى الحجز، مع
  `payment: null` و`payment_error`. والحجز المجاني لا دفعة له: `payment: null`
  و`payment_error` = "لا يوجد مبلغ مستحق".
  الحجز المتعدد (`/batch`) يقبل `wallet` أو `cash` فقط.
- **الفعالية:** `POST member/events/{id}/register` يقبل `payment_method`
  و`wallet_owner_type/id`. البطاقة أو النقد يؤكدان المقعد **غير مدفوع**، ولا
  يُسمح بالدخول قبل الدفع. احتفظ بـ`data.ticket_id` لـ(ب).
- **الباقة:** `POST member/memberships` يقبل `payment_method`. `cash` يعيد
  `{"data": {"pending_purchase": {...}}}` — حجز لمدة 48 ساعة بلا اشتراك حتى
  يدفع العضو في الاستقبال، ويظهر أيضاً في `memberships/current` تحت
  `pending_purchase`. `paymera` يعيد شكل بدء الدفع في القسم 2.

### د. كتلة `payment` في الشاشات

تظهر على الحجوزات (القائمة والتفاصيل)، والجلسة الحالية، وتقرير الجلسة
(`totals.payment`)، وتسجيل الفعالية:

```json
{"state": "unpaid", "method": null, "amount_points": 100, "price": "10.00 $",
 "price_point": "100 pts", "paid_at": null, "payment_id": null}
```

`state`: `paid` | `unpaid` | `pending` (دفع بطاقة جارٍ أو باقة محجوزة للنقد)
| `null` (لا شيء للدفع: فعالية مجانية أو جلسة ما زالت مفتوحة).

`amount_points`: السعر كاملاً بعد الدفع، و**ما بقي مستحقاً** قبله. الحجز
المدفوع ثم المُمدَّد يصبح `unpaid` بمبلغ التمديد وحده، لا بسعر الحجز كله،
وهذا ما يدفعه "ادفع الآن" وما يحصّله الاستقبال.

في الفعاليات (التفاصيل و"فعالياتي" تحت `registration.payment`) الكتلة بهذا
الشكل نفسه، و`pending` يعني دفع بطاقة جارياً و`payment_id` هو ما تستعلم عنه؛
وتكون `null` كلها إن لم يكن لك تسجيل في الفعالية.

في الحجوزات بقي `state` كما كان (`paid`/`unpaid`) حفاظاً على التطبيق الحالي،
والدفع الجاري يظهر في `awaiting_payment: true`.

### هـ. زر "ادفع الآن"

كل ما هو `unpaid` في الكتلة أعلاه يُدفع لاحقاً بمسار عمليته نفسه (ب): الحجز
بـ`booking_id`، وتسجيل الفعالية بـ`ticket_id`، والجلسة المغلقة بمسار `pay`.
الجلسة المفتوحة لا تُدفع قبل إغلاقها (422).

## 12. العروض وكوبونات الحسم

التصميم كاملاً في `docs/decisions/pricing-offers-and-coupons.md`. ما يحتاجه
التطبيق:

### أ. لا تحسب السعر بنفسك

**لا تحسب سعر الحجز من `سعر الساعة × المدة` بعد الآن.** العرض على مساحة
يُطبَّق على الدقائق الواقعة داخل فترته فقط، فقد يغطي جزءاً من الحجز. السعر
الصحيح، بالعرض وخصم الباقة والكوبون، يأتي دائماً من الخادم:

```http
POST /api/v1/member/bookings/preview
{"space_id": 4, "start_at": "2026-10-06 10:00", "end_at": "2026-10-06 12:00", "coupon_code": "WELCOME20"}
```

التفصيل (`breakdown`) يضيف سطرين جديدين بجانب سطر خصم الباقة (`discount`):
`sale` (توفير العرض) و`coupon` (خصم الكوبون).

### ب. كتلة `sale` في المساحات والباقات

تظهر في قائمة المساحات وتفاصيلها (`details.sale`) وفي قائمة الباقات
وتفاصيلها (`sale`). قيمتها `null` إذا لم يكن هناك عرض قائم الآن:

```json
"sale": {
  "points": 80,
  "original_label": "10 $ / ساعة",
  "sale_label": "8 $ / ساعة",
  "ends_at": "2026-10-12T09:00:00+03:00",
  "ends_label": "ينتهي العرض في 2026-10-12 09:00"
}
```

اعرض `original_label` مشطوباً وبجانبه `sale_label`، و`ends_label` تحتهما.
النصوص جاهزة بلغة الهيدر `lang` وعملة الهيدر `currency`.

### ج. زر "تطبيق" للكوبون

```http
POST /api/v1/member/coupons/preview
```

| `purpose` | مع |
|---|---|
| `plan_purchase` | `plan_id` |
| `booking` | `space_id` + `start_at` + `end_at`، أو `payable_id` لحجز غير مدفوع |
| `coworking_session` | `payable_id` لجلسة مغلقة غير مدفوعة |
| `event_registration` | `event_id`، أو `payable_id` لتسجيل غير مدفوع |

```json
{
  "data": {
    "coupon": {"code": "WELCOME20", "applied": true, "points_discounted": 24, "message": null},
    "list_points": 120,
    "list_price": "12 $",
    "price_points": 96,
    "price": "9.60 $",
    "lines": [{"key": "base", "points": 120}, {"key": "coupon", "points": -24}]
  }
}
```

لا يُنشئ شيئاً ولا يستهلك الكوبون. مفاتيح `lines`:
`base` | `sale` | `plan_discount` | `coupon`. الحد 20 طلباً في الدقيقة.

### د. إرسال الكوبون مع الشراء

حقل اختياري واحد `coupon_code` على:
- `POST bookings` و`bookings/batch` و`bookings/preview`
- `POST memberships` (لا يُقبل مع `company_id` حالياً)
- طلب الدفع على حجز / جلسة / تسجيل غير مدفوع: `POST bookings` مع
  `booking_id`، و`POST events/{id}/register` مع `ticket_id`،
  و`POST coworking-sessions/{type}/{id}/pay`. لا يُقبل مع شحن المحفظة.
- `POST events/{id}/register`
- `GET payment-methods` (مع `plan_id` أو `payable_id`)، فيصير `amount_points`
  هو السعر بعد الكوبون.

ردّ الحجز والباقة والدفع يحمل:

```json
"coupon": {"code": "WELCOME20", "applied": false, "points_discounted": 0,
           "message": "العرض الحالي يمنحك سعراً أقل، لذلك لم يُطبَّق الكود."}
```

`applied: false` مع رسالة يعني أن الكوبون لا يُجمع مع العروض وأن العرض الحالي
أرخص، فتمّت العملية بسعر العرض. اعرض `message` كما هي.

الأمر نفسه عند الدفع بمعرّف سجل موجود (`booking_id` أو `ticket_id` أو مسار
`pay`): الكود الذي لا يُجمع مع العرض الحالي، أو الذي يصل والسجل عليه دفعة
قيد التنفيذ، لا يُرفض بل يعود `applied: false` مع سبب في `message`، ويمضي
الدفع بسعر السجل الحالي.

في تسجيل الفعالية (الإنشاء) لا توجد كتلة `coupon`: السعر بعد الكوبون هو
`price_points` للتسجيل نفسه. والكوبون الذي يجعل الفعالية مجانية يؤكد المقعد
مدفوعاً. أما الدفع بـ`ticket_id` فتأتي الكتلة داخل `data` (القسم 11-ب).

### هـ. رفض الكوبون — 422

```json
{"message": "انتهت صلاحية هذا الكود.", "reason": "expired"}
```

اعرض `message` كما هي، واستخدم `reason` للمنطق فقط:
`not_found` | `not_started` | `expired` | `usage_limit_reached` |
`per_user_limit_reached` | `not_eligible` | `new_members_only` |
`not_applicable` | `min_amount_not_met` | `not_combinable` |
`already_applied` | `payment_in_progress`. (عند الدفع بمعرّف سجل موجود
يخرج `not_combinable` و`payment_in_progress` من هذه القائمة: يعودان ردّاً
ناجحاً بـ`applied: false` كما في 12-د.)

الكوبون الذي يجعل الباقة مجانية يفعّلها فوراً بلا دفع. وإلغاء الحجز، أو فشل
البطاقة، أو انتهاء مهلة الدفع النقدي، يعيد استخدام الكوبون للعضو تلقائياً.
